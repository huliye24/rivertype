## 二、这次会话里 AI 反复"想到与尝试"的事

以下每一项都是会话级默会知识，AI 不被显式告知就得自取：

### T-1 · 源文件结构识别

每章 markdown 顶端必有：

```
> 译文说明：……
> 体例：……

---

正文……
---

## 第N章 注释
1. ……
```

AI 第一次读到这格式时，用约 30 行思考"这是什么 + 怎么剥"——没有任何文档说这要剥。

### T-2 · 术语保留规则

希腊文（*tokos en kalo*）、德文（*Hervorscheinen*, *das Verbindliche*）、拉丁文（*homo doloris*）原文保留、斜体、中文括注。这是哲学翻译的核心，但没有任何文件说明。

### T-3 · 古典节奏的选用

译文中主动用"于...之中"、"之"链接，而非"在...里"、"的"。这是风格选择，不在源文中显式。

### T-4 · 概念加粗

**美**、**他者**、**同一者**、**Eros**——无论原版是否黑体一律加粗，作为概念标记。AI 第一次必须想到"加粗是给中文读者做的概念高亮，不是译字"。

### T-5 · 章节命名格式

`# 第N章 中文名`，中文章次用一、二、……、十四。阿拉伯数字 1、2、…、14 在中文语境内不够古典。

### T-6 · 直接引文与署名

用 `> blockquote`；署名用 `<p align="right">— 作者</p>`。这是 HTML 嵌入 markdown 的混合写法。

### T-7 · 书名候选生成

中文译名生成，要跨 4 种风格（直译、留存、存在论、修辞）给出 5–8 个候选，让用户挑。这本身是一种"AI 决策外包"机制。

### T-8 · 构建流水线

预处理脚本剥头尾 → markdown 入口清单 → theme.css → Vivliostyle 配置 → EPUB。Vivliostyle 的具体语法（`@page`、`page-break-after:always`）要 AI 自己查。

## 四、建议的具体扩展

### 4.1 新增 Prompt

> **`docs/prompts/translate-philosophical.md`** —— 现代英语哲学 / 美学 / 人文散文 → 现代汉语

与现有 `vernacular.md`（古汉 → 现代汉）和 `english.md`（古汉 → 英）并列。这是 Rivertype **第三个翻译方向**——补齐"现代西学 → 现代汉语"这一长期空缺。

Prompt 要写进：
- 术语保留规则（希腊 / 德 / 拉丁 / 法）
- 古典节奏的选用准则
- 概念加粗的判定
- 章节命名 / 引文 / 署名格式
- 书名候选生成机制
- 校验清单

### 4.2 扩展 GLOSSARY

> **`docs/GLOSSARY.md`** 新增一节"**六、转译会话常用术语**"

定义：
- **译文说明块**（translational preamble block）—— 译稿顶端标注译源、版权、体例之块引用；EPUB 发布前应剥除
- **注释块**（notes block）—— 译稿末尾 `## 第N章 注释` 区段；正式发布前应剥除
- **术语保留**（term retention）—— 多语种术语在译文中保留原字、斜体、括注中文
- **概念加粗**（concept emphasis）—— 关键概念词无论原文是否强调一律加粗，作为中文读者之概念索引
- **古典节奏**（classical cadence）—— 译文选用"之、于...之中、毋宁"等文言连接以承载哲学分量
- **书名候选机制**（title candidacy）—— AI 应在用户未定名时跨 4 种风格生成 5–8 个候选供挑选

### 4.3 协议扩展方向（待 RFC）

> **`docs/protocol/RTP-0.1.md` → RTP-0.2 草案**

考虑增加一个新区段：

```
<!-- @section: chinese-philosophical -->
## 现代汉语译
```

与 `vernacular`（古籍白话）并列，作为"现代外语 → 现代汉语"的协议锚点。该区段须遵守：

1. 章节格式：`# 第N章 中文名`（中文章次）
2. 概念加粗：`**...**`
3. 术语保留：`*原文术语*（中文）`
4. 直接引文：`> 引文` + `<p align="right">署名</p>`
5. 译文说明块（顶端）与注释块（末端）在发布阶段剥除

### 4.4 工具扩展

> **`tools/build_epub.py`** —— 把 .md 译稿合订为 EPUB

输入：`transcripts/<work_id>/chapters/*.md`（每个文件为一章）
输出：`builds/<work_id>.epub`

流水线：
1. 剥除每章顶端的 `> 译文说明... > 体例... ---` 块
2. 剥除每章末端的 `## 第N章 注释...` 块
3. 注入扉页（`templates/cover.md`）：标题 / 副题 / 署名 / 目录
4. 注入主题 CSS（`themes/<theme>.css`）
5. 调用 Vivliostyle 构建

—— 这把会话中的 `preprocess.js` + 临时 `vivliostyle.config.js` + 临时 `theme.css` 上升为可复用 CLI。

### 4.5 工作流扩展

> **`WORKFLOW.md`** 增加第九步"现代外语 → 现代汉语"路径

与现有"古籍 → 白话"主路径并列（Step 0–8）。新路径可省去校勘、断句（古汉没有这些），但需新增：

- **T-0 译源确认**：明确英文版的版本（英译本 vs 德文原作）、出版社、年份
- **T-1 译注剥离**：与古籍的"原文一字不改"对称，现代译稿的"译文说明 + 注释"应在发布阶段剥除
- **T-2 书名决议**：跨风格候选机制

## 五、原则声明：Rivertype 的"AI 原生"边界

Rivertype 不是替 AI 思考。它做的是：

> 把"任何领域专家在转译开始前都会默会知道的事"，显式化为协议 + 提示 + 工具；
> 让 AI 每次新会话开始时就能站在这个累积的知识底座上工作。

由此 AI 的"能力边界"被扩展——不是变聪明了，而是把已知知识当默认，省下来去处理真问题（领域取舍、文风、判定）。

这次会话是这个原则的一个具体演示。8 项默会知识中，7 项可被编码；剩 1 项（构建流水线的语法细节）属于工具层，工程上需要做但不是协议层问题。
